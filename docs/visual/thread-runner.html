Fire and forget, or nothing else works

POST /api/threads returns 202 as soon as the thread exists. The agent run is a detached promise. That single decision is what makes concurrent threads possible at all — a create endpoint that waited for the model would serialise every thread at the HTTP layer, and the whole feed would be theatre.

The run, and the block that ends it

Without it, a thrown ADK stream would leave a thread on streaming forever — a blinking caret on a run that ended, with nothing in the UI to say so and no way for the client to find out.

Sequence numbers are assigned in exactly one place

private emit(hub, threadId, draft) {
  const seq = (this.sequences.get(threadId) ?? 0) + 1;
  this.sequences.set(threadId, seq);

  // Validating on the way out means a protocol mistake fails in the
  // server's own tests rather than as a dropped frame in the browser.
  const event = parseFeedEvent({ ...draft, threadId, seq, ts: Date.now() });
  hub.publish(event);
  return event;
}

Every draft from the translator passes through here. One counter, one increment site, one place to get it wrong — which matters because a skipped seq is not cosmetic: the client buffers against a gap that never closes and the thread stalls permanently.

Why validate on the hot path

Every event, including every token delta, is parsed through zod. That is a real cost, taken deliberately: a malformed event fails loudly in the server's own test run instead of vanishing silently in a browser. If profiling ever justified it, validating in development only is the change — not removing it.

The same counter reports itself

summaries(sessionId) serves GET /api/threads, and the lastSeq it reports comes from the very map emit increments. One counter assigns sequence numbers and one counter answers "where has this thread got to" — they cannot disagree, because they are the same thing.

summaries(sessionId) {
  return this.list(sessionId)
    .sort((a, b) => a.createdAt - b.createdAt)
    .map((thread) => ({
      id: thread.id, prompt: thread.prompt, agent: thread.agent,
      status: thread.status, createdAt: thread.createdAt,
      // the same map emit() writes to
      lastSeq: this.sequences.get(thread.id) ?? 0,
    }));
}

This is the foundation of the resync recovery path. When a client's resume point falls out of the SSE replay buffer the server sends a resync notice; the client fetches this snapshot and rebuilds the threads it is missing. It does not seek forward to lastSeq — the replay that follows usually contains the very events it would have skipped — so the value serves only as the hint that a rebuilt thread has history worth warning about. Identity and status are recoverable; the transcript is not, because events live only in that buffer. The wire-level exchange is on One Wire, Many Threads, and what the client does with the snapshot is on Four Gates and a Drain (traces G and H).

Sorted by createdAt so a rebuilt feed comes back in the order it was originally rendered.

Two state machines, stepped together

The publish helper applies assertTransition to the thread record whenever the translator emits a status. The record and the translator therefore advance in lockstep, and any divergence between them throws immediately rather than producing a UI that slowly drifts from reality. That assertion has already earned its place once.

Isolation: a fresh tree and a private session per thread

01A new agent tree per thread

ADK agents hold a parentAgent back-reference, so a single instance shared across concurrent threads corrupts transfer routing. createAgent is called inside run, once per thread. Construction is cheap; correctness is not.

02One ADK session per thread

getOrCreateSession({ userId: sessionId, sessionId: thread.id }). Threads are independent conversations, so sharing a session would leak one thread's history into another's model context. The browser session is the user; the thread is the conversation.

The store those sessions live in is injected: ThreadRunner takes a BaseSessionService rather than constructing one, and the sessions provider decides whether that is ADK's in-memory implementation or DatabaseSessionService against Postgres. ADK's own interface is the port, which makes this the cheapest real swap in the repo — see The Substrate Line.

This is also the groundwork for follow-up messages: history already accumulates in that session, so a second turn needs a route and a composer rather than a redesign.

03Cancellation goes straight into ADK

An AbortController per thread, its signal passed to runAsync. cancel() is idempotent and a no-op on a finished thread, which is what makes the route's 202 / 409 / 404 distinction meaningful rather than decorative.

Trace these yourself

  1. A thread's ADK stream throws on its third event. What does the client see, and in what order?
  2. Two threads start in the same millisecond. Can their events collide on seq? On offset?
  3. cancel() is called twice in quick succession. What does each call return, and what does the client observe?
  4. Why does start() publish thread.created itself rather than letting the run emit it?
Answers

1. Everything published before the throw, then thread.error, then thread.status: error — reason before state — and any half-written message is closed by finish. 2. Not on seq: it is keyed per thread. Not on offset either: the hub is a single writer in a single-threaded runtime. 3. The first returns true (202), the second false (409) because the signal is already aborted; the client sees exactly one cancelled status. 4. So the thread exists before any agent work happens: the UI renders it immediately, and seq 1 is guaranteed to be the creation event for every thread.
