No Sleeps, No Selectors

Two rules, and everything else follows

A streaming UI is mostly timing, and timing is where browser suites rot. Two constraints keep this one from becoming the kind of suite people re-run until it passes.

RULE 1Zero waitForTimeout

Not "few". Zero. Every assertion is web-first — expect(locator) — so Playwright retries until the condition holds or the timeout expires.

A fixed sleep in a streaming test is a race that has not failed yet. It passes on the machine it was written on and fails on CI, where everything is slower and nothing is your fault. The fix is never a longer sleep.

What zero sleeps does not buy you

Removing fixed sleeps removes one class of race. It does not remove the class where the application finishes before the test can act on it — and that one hides until a loaded CI runner finds it.

Both cancellation specs did exactly this. A scripted research thread runs to completion in about a second at the default 25ms chunk delay, and the specs have to get from "the first message is visible" to "the Stop click landed" inside that window. Locally they always did. On a loaded runner they did not, so Stop unmounted mid-click and Playwright reported a detached element thirty seconds later — a timeout that says nothing about the cause.

The fix widens the window rather than retrying into it: SCRIPTED_CHUNK_DELAY_MS: '60' on the Playwright web servers only. Unit tests never start a server, and CI wall-clock here is dominated by installing browsers, not by streaming. The click is now separately bounded at 5s so the two failures read differently — Stop never appeared against Stop appeared and went away mid-click.

Verified by driving it the wrong way: at a 1ms delay the specs fail on demand, which is what makes the 60ms a fix rather than a hope.

RULE 2No spec ever touches a selector

Specs speak in "the thread whose prompt is X" and "its status". e2e/pages/FeedPage.ts owns every mapping from that vocabulary to a data-testid.

The subtle half: every accessor returns a Locator, never a resolved value. A helper that returned a string would resolve at call time, and the auto-waiting would be gone — which is how waitForTimeout gets back in through the abstraction that was supposed to prevent it.

The fourth layer, and why it had to exist

Three test layers were green while the resync feature was broken. Three separate times.

The bugs, in the order they shipped: a client that reconnected with no resume point and so triggered a fresh notice forever; a rebuilt thread that adopted the snapshot's lastSeq as a watermark and discarded the replay that followed; and a fresh page load taking a branch of the overrun check that only handled resuming clients. Each is L1. Each was found by driving a real browser.

Verified, not assumed

The recovery project was checked against the bugs it claims to catch by reintroducing the watermark bug on purpose: two browser tests and five reducer tests went red, then the change was reverted. A regression test nobody has watched fail is a hypothesis.

The fixtures that make failures legible

Console errors fail the test

The consoleErrors fixture catches the class of bug that leaves the UI looking correct while React throws quietly in an effect — exactly what a streaming app is prone to. A test that intends to break something declares it:

allowConsoleError(testInfo, /establish a connection/, 'the stream is blocked deliberately');

Per-test, via an annotation, rather than a per-file test.use option. Two things follow: the guard stays strict everywhere else instead of being weakened for a whole file, and the suppression shows up in the HTML report with its reason attached — so a reader can see which tests suppress what, and why.

The ignore list is patterns rather than strings because the engines disagree on wording: Chromium writes net::ERR_, Firefox writes prose for the same failure.

Accessibility, tested twice

@axe-core/playwright scans the empty, streaming, errored and dark-mode states. Separate assertions cover what axe cannot judge — whether the right content is live.

The judgement axe cannot make

A feed that announces every streaming token is technically conformant and practically unusable. So the specs assert that streaming prose is not in a live region, and that each thread has exactly one live region carrying its status. Conformance is a floor, not the goal.

The scan has already paid for itself: it caught two genuine contrast failures in the light palette — 4.49:1 against a 4.5:1 threshold, and an error code made translucent for visual weight, which dropped it below the line.

Both engines, for a specific reason

Chromium retries a dropped EventSource indefinitely. Firefox gives up on some failures and parks the connection in CLOSED, where nothing reopens it. That bug was found by running the suite in Firefox, and the fix — an explicit readyState watch in useFeedStream — is guarded there. See One Wire, Many Threads for the manual resume path it needs.

Firefox skips a11y.spec.ts: the axe rules being checked are engine-independent, and running them twice buys nothing but wall-clock.

Trace these yourself

  1. Run pnpm exec playwright test --project=recovery, then set EVENT_RETENTION=500 on the :3002 server and run it again. Which of the four tests still means anything?
  2. Change one FeedPage accessor to async and return await locator.textContent(). Find a spec that goes flaky, and say which retry you removed.
  3. concurrency.spec.ts asserts that interleaved threads keep uncorrupted text. Which server-side invariant would have to break for it to fail — and which reducer gate would catch it first?
  4. Comment out the allowConsoleError call in the reconnect test. What fails, and is the failure about the app or about the test?
