The seam

This is the only file in the repo that speaks both ADK and the wire protocol, and it is deliberately the only one. Everything downstream — the reducer, the React components, every Playwright assertion — is written against FeedEvent, so swapping ADK for another framework is a rewrite of this file and nothing else.

The Map that matters

ADK emits one flat stream for an entire agent tree. With a ParallelAgent, two sub-agents emit interleaved partial text on the same invocation. This is the case that breaks a naive adapter.

The same property is why the message id is minted per author rather than per event: deltas need a stable target to accumulate into, and a message.complete needs to land on the message its deltas built.

One event, several drafts — in a deliberate order

A single ADK event can carry text, tool calls and tool responses at once. translate emits them in a fixed order, and each position is a decision.

Why the error comes first

A consumer that stops reading once a thread reaches a terminal status must already hold the reason. Emitting thread.error before thread.status: error guarantees it. This is asserted directly in adk-adapter.test.ts — and it was found by a test that stopped at the first terminal status and never saw why.

Who owns the status

Exactly one object writes thread status: the translator. Three methods do it, and the discipline is that nothing else may.

methodemitswhen
begin()runningonce, before the ADK stream is consumed
translate()streaming, awaiting_tool, awaiting_input, running, errorderived from each ADK event
finish()complete / error / cancelledonce, in the runner's finally
The bug that made this a rule

ThreadRunner used to publish the opening running status itself instead of calling begin(). The translator stayed on queued, so its next transition was computed from the wrong state, dropped as illegal, and the two machines diverged until assertTransition threw and failed the whole thread.

It cost about five minutes to find, because the assertion was loud. That is the argument for a server that throws where the client forgives.

Illegal transitions are dropped here, not thrown

setStatus returns nothing when a transition is illegal or unchanged. ADK can emit a trailing event after a run is already cancelled, and losing that race must not take the server down. assertTransition — the throwing variant — is applied one level up in ThreadRunner, where the transitions are ours rather than the framework's.

Three details worth knowing

01A one-shot message does not claim to have streamed

The message.complete branch emits no status change. If the message streamed, the thread is already streaming; if it arrived whole, the thread never was, and saying otherwise is a lie the UI renders as a caret that never blinked.

02Transfer is shown; framework requests are not

transfer_to_agent is surfaced as an ordinary tool.call, because a handoff is meaningful to a reader. The adk_request_* family is control-plane, so it moves the thread to awaiting_input and renders nothing. Same shape in ADK, opposite treatment.

03finish() flushes what the stream left open

A run that ends mid-message — cancelled, or thrown — leaves an entry in openMessages. finish emits a message.complete for each before the terminal status, so no thread is left with a blinking caret on a message that will never continue.

Trace these yourself

  1. An ADK event carries a functionResponse and a functionCall in the same parts array. What drafts come out, and in what order?
  2. Two agents stream concurrently and one finishes. What happens to the other's entry in openMessages?
  3. A trailing partial-text event arrives after finish('cancelled'). What is emitted, and what is the thread's status afterwards?
  4. Why does the translator emit drafts without seq instead of numbering them itself?
Answers

1. tool.result, then thread.status: running, then tool.call, then thread.status: awaiting_tool — results before calls. 2. Nothing: entries are per author, so one agent completing does not touch another's. 3. A message.delta is still emitted (the text is real), but the status stays cancelled, because streaming is not reachable from a terminal state and setStatus drops it. 4. Sequence numbers are the thread's ordering guarantee; assigning them in one place (ThreadRunner.emit) is what makes them impossible to drift.
