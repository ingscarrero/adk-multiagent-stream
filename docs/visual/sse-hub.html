One connection, every thread

A browser session opens exactly one SSE connection, and every thread's events travel down it. Not one stream per thread — browsers allow six concurrent HTTP/1.1 connections per origin, so per-thread streams break at the seventh concurrent thread, and only under concurrency, which is the condition a demo never hits and production always does.

One counter cannot do both jobs. A global counter cannot express per-thread order once threads interleave, and a per-thread counter cannot drive Last-Event-ID on a shared connection.

The handshake, and the byte that makes it work

Replay, and the two ways to be missing a prefix

The buffer holds the last 500 events per session. A client that reconnects inside that window is caught up silently. A client outside it needs to be told, and there are two quite different ways to be outside it.

How the second branch was found

The first version of the fix handled only the left branch. Tests passed at three layers — server, reducer, and hook — because all three exercised a resuming client. Driving a real browser against a four-event buffer showed a page reload still losing the thread entirely.

Layered tests prove each layer. They do not prove you enumerated the cases.

The exchange, frame by frame

A browser reloading into a session whose buffer has already rolled. This is what actually crosses the wire:

GET /api/stream?sessionId=S            (no Last-Event-ID -- a fresh page)

retry: 1000
: connected

event: resync
data: {"from":156}

id: 156
event: feed
data: {"type":"message.delta","threadId":"thr-a","seq":19, ...}
... the rest of the buffer, starting mid-thread ...

The client stops there, fetches the snapshot, and comes back — resuming from the offset the notice named:

GET /api/threads?sessionId=S          -> { threads: [ { id, prompt, status, lastSeq } ] }

GET /api/stream?sessionId=S           Last-Event-ID: 155

retry: 1000
: connected

id: 156
event: feed
data: {"type":"message.delta", ...}
... the same replay, and no resync this time ...
The loop this replaced

The first version of the client reconnected with no Last-Event-ID at all — "replay everything you have", which reads as the obvious thing to do. But the overrun test for a client with no offset is oldestHeld > 1, still true the instant it returns, so the server sent another notice immediately.

The stream never stayed up. The visible symptom had nothing to do with reconnection: new threads arrived empty and marked truncated, because live events were being torn down mid-flight. The from field had been in the payload the whole time, unused.

What comes back, and what cannot

The snapshot carries each thread's identity, status and lastSeq — never its transcript. Events live only in this buffer, so anything rolled out is genuinely gone. A rebuilt thread is marked historyTruncated and says so: "Earlier messages were lost" when some survived, "Messages for this thread are no longer available" when none did.

Framing, heartbeat, teardown

01Why the frame format is safe by construction
id: 42
event: feed
data: {"type":"message.delta", ...}

SSE framing is whitespace-sensitive: a literal newline inside data: would split the frame. JSON.stringify cannot emit one — it escapes newlines as \n — so no payload can break the envelope. Worth knowing as a property, not a hope.

02The heartbeat is a comment

A line beginning : is invisible to EventSource consumers but keeps the socket warm. Idle proxies close quiet connections, and a multiplexed feed can legitimately be idle for minutes. The interval is unref'd so it never holds the process open, and it only runs while someone is listening.

03Buffering happens with zero subscribers

publish writes to the buffer whether or not anyone is connected. A thread started before the stream opens — or while the browser is reconnecting — must not lose its events, and this is what makes the late-subscriber case work at all.

04Storage and delivery moved out

This class used to own the buffer, offset assignment, retention, replay and who gets each frame. Those are now the EventStream provider. What is left here is the part that is genuinely about SSE — headers, the priming frame, framing, the resync notice, the heartbeat, and subscriber teardown.

One port rather than two, because only two of the four log-and-delivery combinations are coherent, and every real provider serves both from one primitive. In-process it is an array and a set of listeners; with PROVIDER_EVENTSTREAM=redis it is Redis Streams, and this file cannot tell the difference.

The open/flush shape is a race fix. A subscriber needs the backlog and everything after it. Calling replay() then subscribe() drops whatever lands between the two, so open does both at once and holds live entries until the caller has written the backlog.

05Two things this file does not do

Backpressure. subscriber.write(frame) discards its return value. Node returns false when the socket buffer is full and then queues in memory without bound, so one stalled consumer grows the server for as long as it stays connected.

Eviction. HubRegistry creates hubs on demand and only removes them at shutdown. The buffer is bounded per session; the number of sessions is not, which is the wrong half to have bounded.

Trace these yourself

  1. Two threads are streaming. Thread A is at seq 9 and thread B at seq 2. What is the next id: on the wire?
  2. A client reconnects with Last-Event-ID: 60 and the buffer holds offsets 45–544. What does it receive?
  3. Same buffer, but the client sends no Last-Event-ID. What does it receive, and why is that different from the case above?
  4. The feed is idle for two minutes with one subscriber. How many bytes cross the wire, and what are they?
Answers

1. Unknowable from the seqs — offset is per session and independent of both. That independence is the point. 2. Offsets 61 upward, no resync: 60 is inside the window. 3. The whole buffer and a resync, because oldestHeld is 45 rather than 1, so the session's start is already gone. 4. Eight heartbeat comments at the default 15s interval — invisible to the client's handlers, and the reason the connection survives a proxy.
