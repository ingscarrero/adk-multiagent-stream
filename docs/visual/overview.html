In one paragraph

Several AI agent threads stream at once over a single connection. Messages stay in order within each thread, every thread's status tracks its own lifecycle, and the whole thing — including the streaming — is tested without an API key.

  
The hard partNot "show a chatbot". Keeping N concurrent agent runs ordered, attributable and recoverable over one wire
The transportOne multiplexed SSE connection for the whole session, not one per thread
The agents@google/adk v2.0.0 — a router that transfers to specialists, and a pipeline that fans out in parallel then synthesises
The trick that makes it testableA deterministic in-process model, so "the concatenated deltas equal the final text" is a reasonable assertion

Prompt to pixel

One prompt's complete round trip. The shape worth noticing is that it is a circuit: the request goes down and the answer comes back on a different path.

The one thing to take from this diagram

The POST returns before any agent work happens. POST /api/threads answers 202 with a threadId and nothing else — the run is detached, and every observable consequence of it arrives later on the SSE connection, correlated by that id.

That split is what makes concurrency tractable. The request path has no long-lived state and cannot block; the stream is single-writer, which is what makes the ordering guarantees provable. The same shape covers cancellation: POST /api/threads/:id/cancel returns 202/409/404 for accepted or not, and the thread actually reaching cancelled is observed back on the stream.

Seven packages, and one line that matters

Three things fall out of that line, and they are the reason it is drawn where it is:

  • The reducer is testable with array literals. No framework, no network, no timers — which is why the ordering tests can afford to be exhaustive.
  • Replacing ADK means rewriting the adapter and the agents package, and touching nothing a user can see.
  • The UI cannot depend on an ADK detail by accident, because it cannot see one.

What one turn actually looks like

"Where is my order, can you track shipping?" — 23 events, and every one of them is a rendering decision.

One turn, because a thread may have several. A follow-up starts another run in the same thread and pays four of the five fixed events rather than five — there is no second thread.created, and it opens with a message.user instead.

What each area of the stack demonstrates

Where to look, per technology, and the non-obvious thing in each.

REACT 19Ordering logic lives in a pure reducer, not in components

apps/web/src/feed/ — reducer.ts, useFeedStream.ts, ThreadCard.tsx, MessageBubble.tsx, ToolStep.tsx, Composer.tsx, StatusChip.tsx.

The reducer is a pure function over a FeedEvent, so every hazard a real stream produces — out-of-order frames, duplicates after reconnect, gaps that never close, two agents interleaving — is an array literal in a test rather than a browser race. The hook owns the connection and nothing else; the components are presentational. See Four Gates and a Drain.

MEMORYThree ceilings, because a long-lived connection has three ways to grow
What growsBoundWhat happens at the limit
Events kept for one sessionEVENT_RETENTIONOldest roll out; a client below them is told to resync
Number of sessionsSESSION_IDLE_TTL_MSA hub with no subscribers, gone quiet, is swept — and its log dropped with it
Bytes queued for one subscriberSSE_MAX_BUFFERED_BYTESThe subscriber is disconnected; it reconnects and resumes

The middle row is the one that is easy to miss. Retention bounds how much is kept per session, which reads like the whole answer and is half of it — every browser tab that ever connected is a session, and nothing bounded how many of those there were. Sweeping the hub alone would not have fixed it either: a hub is a Set and a timer handle, while the events are the memory, so the sweep drops the session's log too.

The third row is a design decision rather than a threshold. res.write returning false is normal — the socket buffer filled and Node took over queuing, which a healthy consumer drains in milliseconds — so the ceiling sits on the queue length, not on the return value. Otherwise an ordinary burst disconnects people.

NODE + EXPRESS 5Seven routes, one of which never ends

GET /api/stream is the long-lived one. POST /api/threads starts a detached run, POST /api/threads/:id/messages continues one, POST /api/threads/:id/respond answers a paused one, POST /api/threads/:id/cancel aborts a signal, GET /api/threads is the recovery snapshot, and GET /api/health reports which provider backs each capability.

Three of those are the same operation wearing different clothes: run again against the thread's existing ADK session with a different message. A prompt opens it, text continues it, and a functionResponse quoting ADK's interrupt id resumes a run paused on a human decision. History accumulates in that session, which is why a follow-up can be answered from an earlier turn without re-sending anything.

The detail that cost real debugging: an SSE endpoint must write a body byte immediately. flushHeaders() flushes your response, but an intermediary has its own, and Node will not put those headers on the wire until a body chunk exists — so EventSource sits in CONNECTING until the first heartbeat fifteen seconds later. See One Wire, Many Threads.

PLAYWRIGHT81 runs, zero fixed sleeps, and a project for the untestable case

Three projects over four servers. Chromium and Firefox run against the default pair; recovery runs against a second server with a 40-event retention, because a replay-buffer overrun on the 500-event default needs about twenty-five prompts and is therefore never tested by accident.

That fourth layer exists because three unit layers were green while the recovery feature was broken, three separate times. See No Sleeps, No Selectors.

CONVERSATIONAL UXNine moments where a plausible build misleads the user

This is the area with no single file behind it, and the one that is easiest to get wrong while every test still passes. An agent run has a handful of moments where the honest thing to render and the obvious thing to render are different — and the obvious one looks fine to whoever built it.

The section below works through all nine: what the moment is, what a reasonable-looking build does, and what this one does instead. Each is pinned by a named browser test, so they are claims that can be checked rather than taste.

GOOGLE ADKTwo agent shapes, chosen to stress a feed differently

router — one thread whose author changes mid-stream via transfer_to_agent. research — two agents emitting interleaved partial text on one invocation, then a synthesiser. The second is the case that breaks naive feeds: without a per-thread seq and a per-author messageId, two agents streaming at once produce one scrambled message.

Four v2.0.0 behaviours are pinned by named regression tests: transfer_to_agent takes agentName not agent_name (the wrong spelling is a silent no-op); transfer rewrites history into synthetic "For context:" user messages; StreamingMode.BIDI throws; and SequentialAgent/ParallelAgent are deprecated in favour of a Workflow API that cannot yet be an LlmAgent sub-agent. See Many Authors, One Feed.

How to read this table

The pattern running through every row: the system's internal state is not the user's mental model, and the gap between them is where a feed either earns trust or loses it.

The server knows a thread exists the moment it is created, that a tool is running, which agent is speaking, and that a transcript rolled out of the retention window. In each of those moments the plausible build lets the user infer the state from the absence of something — and absence is ambiguous. Nothing on screen means thinking and crashed equally well. An unlabelled message means the router answered and the specialist answered equally well. An empty thread means no messages yet and your history is gone equally well.

Every decision above resolves one of those ambiguities in the user's favour, and each costs something — an extra event, a wider protocol, a second wording to maintain. That is the trade the column headings are there to make visible.

Two that are only half-won

Lost history could be named but not recovered — until the message store landed. A restored thread used to say its messages were gone, and a long session degraded into mostly those notices. The transcript now comes from a store with no retention window, so a rebuilt thread arrives whole however far the stream has rolled past it (L16, fixed). What survives is the emulated adapter: with the memory store a restart still loses everything, which is the open half of L7.

A denied action needs an answer written for it. The scripted model reaches the same script position whether an approval was granted or refused, so the first version of the confirmation gate reported a denied refund as applied — while every other assertion passed. Fixed with rejectedText, the one place a script reads a tool result rather than counting rounds. A real model reads the refusal payload; a fake has to be told about it.

Stop is built, tested, and effectively invisible. The control renders only while a thread is non-terminal, which is right — offering to cancel something already finished is worse than not offering it. But at the default scripted pacing that window is 465 ms for the router and 657 ms for the research pipeline, measured off the wire. Nobody can notice a button appear, decide to use it and reach it in that time, so the feature reads as missing to anyone evaluating the app by hand.

With MODEL_MODE=gemini a thread runs for seconds and Stop is comfortably reachable, so this is an artefact of the scripted model being fast on purpose — the same property that makes the suite deterministic. It is still a real problem, because the first thing anyone does is pnpm dev and send a prompt, and a capability nobody can observe is indistinguishable from one that does not exist. Raising the pacing makes it plainly visible:

pnpm dev:demo
// SCRIPTED_CHUNK_DELAY_MS=200 TOOL_LATENCY_MS=400
// the window becomes 2.0s (router) and 4.2s (research)

Shipped as a second way to run it rather than a new default: dev is what the tests exercise, dev:demo is what a person watches. Changing the default would slow the first thing every reader sees to fix a problem that only appears under hand-evaluation, and would leave CI on different pacing from pnpm dev for no benefit.

The same root cause already bit the browser suite — the cancellation specs could not reliably click Stop either, which is why playwright.config.ts pins SCRIPTED_CHUNK_DELAY_MS: '60'. That fix went to the tests and not to the human. Recorded as L17.

The three decisions worth defending

DecisionThe alternativeWhy this one
One multiplexed SSE connectionOne stream per threadBrowsers allow six concurrent HTTP/1.1 connections per origin. Per-thread streams hang at the seventh — only under concurrency, which is the condition a demo misses and production hits
A deterministic in-process modelTest against the real APITiming tests against a live LLM are re-runs and hope. This is what makes "the concatenated deltas equal the final text" assertable
The browser never sees ADKShare types from the frameworkThe reducer stays testable with array literals, and the wire contract survives replacing the agent runtime
The one to raise before you are asked

Nothing survives a restart. Sessions, thread records, the event log and the transcript all live in process. Sessions, the log and the transcript each have a port — so for those three the real adapter is a config change rather than a redesign, and not one of those adapters is written. Thread records do not: the registry is a private map in ThreadRunner, and the recovery snapshot enumerates it.

The architectural half of this is done and worth separating from the durability half. The event log used to be the message store as well, and everything that felt wrong about recovery followed from that one conflation. It is two ports now: a log that answers what happened next over a window, and a transcript that answers what is this thread and never forgets. See The Substrate Line. What remains is mostly ordinary — swap the adapters — plus one seam that is not: a durable store keeps every transcript across a restart and cannot list the threads to return, so the registry needs a port of its own before "restart" is a config change (L7).
