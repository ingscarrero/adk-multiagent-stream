Four Gates and a Drain

How the feed reducer turns an out-of-order stream of events into ordered thread state — and why every event takes exactly one of three exits.

apps/web/src/feed/reducer.ts

One event in, one outcome out

The reducer is a pure function: (state, event) → state. No network, no timers, no React. Every event that arrives is applied, buffered, or dropped — never partially handled, never silently ignored.

Four gates decide which. They run in a fixed order, and the order is load-bearing: gate 2 can only ask "have I seen this already?" because gate 1 has guaranteed the thread exists.

  • Applied — state moved forward
  • Buffered — held, not lost
  • Dropped — deliberately discarded

What the three outcomes actually mean

The words are precise, not descriptive labels. Each one names a different fate for the event and a different consequence for state — and only one of the three is ever visible on screen.

Applied — the only outcome with a visible effect

applyToThread folds the event into the thread and lastSeq moves to the event’s seq. What actually changes depends entirely on the event type:

eventeffect on thread state
thread.statusstatus moves — but only if the transition is legal, otherwise silently kept
thread.errorerror is set; the transcript so far is preserved
message.deltatext appended to messages[messageId], created if new
message.completetext replaced wholesale, streaming set false
tool.calltool recorded as pending
tool.resulttool becomes done, original args retained
message.usera follow-up is appended to timeline directly, carrying its own text
thread.input_requiredinputRequest is set — what the thread is blocked on, and what would unblock it
thread.creatednothing — the thread was already built by createThread

message.user is the one timeline entry carried inline rather than by reference. A message and a tool are both updated by later events, so the timeline holds an id and the payload lives in a map. A follow-up is never updated after it arrives — there is no second event to correlate with — so its position is its identity.

thread.input_required is the only event that sets state the status then clears. Leaving awaiting_input removes inputRequest, keyed off the status rather than off the answer landing, because the status is what gets replayed on reconnect. A control that outlived its request would let someone approve the same action twice.

A message or tool seen for the first time also gets appended to timeline, which is what fixes its position in the rendered thread. Applying is the only outcome that then runs the drain.

Buffered — deferred, not rejected

The event is kept. It sits in thread.buffered holding its full payload, waiting for its predecessors. Nothing about the visible thread changes, and lastSeq does not move — which is exactly why a buffered event can’t be mistaken for a delivered one.

Two consequences worth knowing. Memory: the buffer is unbounded on the client, so a permanently open gap grows it for the life of the session. And appearance: a stalled thread looks identical to a slow one. The user sees “Waiting for the agent…” either way, with nothing distinguishing a thread that will recover from one that never will.

Dropped — two different things wearing one name

The event is discarded and will not be re-sent. But why it was discarded matters enormously, and the three drop sites split cleanly into two kinds:

Redundant drops — healthy no information lost

Gate 2 (already applied) and gate 3’s inner check (already buffered). The event’s information is already in state, so discarding the copy is not just safe, it is the correct behaviour. These are the drops that make the reducer idempotent, and you should expect a burst of them after every single reconnect.

Lossy drops — a symptom information destroyed

Gate 1 (unknown thread). The event carried content the client has never seen and never will — the server does not re-send on request. Every one of these is a hole in the feed, and because gate 1 keeps firing for that thread, one lost thread.created means the entire thread is invisible for the rest of the session.

They are counted separately — stats.droppedRedundant and stats.droppedLossy — precisely so the two can be told apart, with totalDropped(stats) for the places where the distinction does not matter. Each of the three drop sites in reducer.ts is labelled REDUNDANT or LOSSY at the point of the increment.

This was one counter until recently, and the split mattered more than its size suggests: droppedLossy is the signal that a thread has gone missing. Buried alongside the replay drops that follow every reconnect, the one number meaning “the feed is incomplete” was indistinguishable from noise.

Recovering from a lossy drop

A lossy drop is no longer permanent. The server sends a resync frame whenever a client is missing the beginning of a session — either resuming from an offset older than anything still buffered, or connecting fresh to a session whose start has already rolled out, which is what a page reload does. The client then tears the stream down, fetches GET /api/threads for a snapshot, dispatches a resync action, and reconnects without a resume point so the server replays everything it still holds.

That second trigger is easy to miss, and was: the first version of the fix handled only the resuming case, and tests at three separate layers all passed while a plain page reload still lost the thread. A fresh client has no stale offset to be wrong about — it simply starts in the middle.

A rebuilt thread is marked awaiting resume rather than seeking forward to the snapshot’s lastSeq. The next event for it is accepted wherever it lands, and its seq answers the only question that matters: arriving at 1 means the replay has the whole thread and nothing was lost; arriving higher means a prefix is genuinely gone. The client does not guess what it missed — it finds out. Traces G and H are the two outcomes, running identical code.

Identity, status and the settled transcript come back: the snapshot reads the message store, which has no retention window, so a thread whose events rolled out of the buffer is rebuilt whole. Hydration from that transcript is the one input that skips the gates, covered below. historyTruncated survives for the case that is still real — the store returned nothing for a thread that has produced events and the client holds nothing either (a restart, with the memory adapter), or the server capped the transcript and said so — and only then does the card say its messages are unavailable.

Reading the counters

droppedRedundant climbing after a reconnect — normal, that is replay overlap. droppedLossy above zero — the feed is missing something; expect a resyncs tick shortly after as recovery kicks in. buffered non-zero and a thread stuck below its neighbours — an open gap; check whether the server skipped a seq. applied flat while the server is streaming — delivering but nothing contiguous, the stalled case.

All four counters live on FeedState but only applied is consumed, as the sticky-scroll trigger in App.tsx. A debug panel is the cheapest observability this app could add, and droppedLossy is the one number worth alerting on.

One honest inefficiency

Every outcome returns a new state object, including the drops — so useReducer re-renders even when nothing changed. Replaying 300 duplicates after a reconnect costs 300 renders with zero visual difference. Returning the identical state reference on a redundant drop would let React bail out entirely; the only reason it doesn’t is that the drop still increments a counter.

The gates, one at a time

Each gate exists because a specific real-world condition produces it. None of them are defensive programming; every one fires in normal operation.

GATE 1 Unknown thread, and not a birth certificate dropped · lossy 
if (!existing) {
  if (event.type !== 'thread.created') { stats.droppedLossy += 1; return state; }
  // otherwise: create the thread, apply, done
}

When it fires: you connected to the stream and the very first event you saw for some thread was a message.delta — no thread.created ever arrived.

Why drop rather than improvise: a thread you invent has no prompt and no agent name. Rendering an anonymous box streaming text from nowhere is worse than rendering nothing. The drop is the honest outcome.

How you get here in practice: the server's replay buffer holds 500 events per session. Reconnect after it has rolled past this thread's thread.created and every subsequent event for that thread is dropped — the thread vanishes. The server sends a resync frame for exactly this case, and the client rebuilds the thread from a snapshot when it arrives — see Recovering from a lossy drop below, and traces G and H. Until that notice arrives, this branch keeps firing and every one of those drops is counted as droppedLossy.

GATE 2 Already applied dropped · redundant 
if (event.seq <= existing.lastSeq) { stats.droppedRedundant += 1; return state; }

When it fires: every single reconnect. Last-Event-ID resumes from the last event the browser received, and the server replays from there — so overlap is the normal case, not an error case.

Why it matters: this one gate is what makes the whole reducer idempotent. Replay the entire stream twice and you get identical state, which is asserted directly in reducer.test.ts.

<= and not <: lastSeq is the highest seq already applied, so an event equal to it is a duplicate too.

GATE 3 Arrived early buffered or dropped · redundant 
if (event.seq > existing.lastSeq + 1) {
  if (existing.buffered.some((held) => held.seq === event.seq)) {
    stats.droppedRedundant += 1; return state;   // already held
  }
  stats.buffered += 1;
  return { ...state, threads: { ...,  buffered: [...existing.buffered, event] } };
}

When it fires: seq 5 shows up while you're still waiting on seq 3. Holding it is the only correct move — applying it would append text in the wrong place, and dropping it would lose content that will never be re-sent.

The nested drop catches a duplicate of an event already sitting in the buffer. Gate 2 can't catch that one, because a buffered event hasn't advanced lastSeq yet.

The buffer is not sorted. Events are appended in arrival order and looked up by seq. There is no ordering invariant to maintain, so there's nothing to get wrong.

GATE 4 Exactly the next one applied 
// implicit: seq === lastSeq + 1
const updated = applyWithDrain(existing, event, stats);

Not a written condition — it's what's left once gates 2 and 3 have excluded everything below and everything above. The event is applied, and then the buffer is drained for as long as it keeps yielding successors.

The one input that skips every gate

A durable transcript is not a transport, and running it through the gates would be a category error.

Recovery now hydrates a thread from the message store before the stream replays anything. Those events go straight into applyToThread — no ordering check, no gap check, no drop counting.

The reason is in what the store keeps. It holds settled events only: everything except message.delta, because a delta exists to show text before it is finished and message.complete carries the authoritative full text anyway. So a transcript's seq numbers have holes, and the holes are exactly where the deltas were.

What gate 3 would do with it

Read every one of those holes as a gap, buffer the entire transcript against predecessors that are never coming, and render an empty thread while holding its whole history in buffered. The gates are not wrong; they are being asked a question about a transport, by something that is not one.

So the rule the gates encode — a missing seq means something was lost — is true of the wire and false of the store. Hydration is the one path where the client trusts its input completely, and it can, because the store is the thing the gates exist to compensate for the absence of.

One gate does carry over: idempotence by seq. A resync can arrive for a thread that is already on screen, and applyToThread appends a message.user unconditionally — there is no id to be idempotent by. Folding the whole transcript onto a visible thread therefore rendered every follow-up twice. Hydration applies only the transcript events newer than the thread's lastSeq, from the status the thread is actually in; a new shell walks the whole transcript from queued.

Nor is an empty timeline evidence of loss. Every stored transcript begins with thread.created, and a thread that has only been created and stepped through a status has nothing to render and nothing missing. historyTruncated is set only when the store returned no transcript for a thread that has produced events and the client holds nothing for it, or when the snapshot says the transcript was capped (transcriptTruncated).

Afterwards the thread is marked awaitingResume and, if the store supplied anything new, restoredFromStore, and the live replay lands on top. Most of it is now redundant — the store already supplied it — which shows up as droppedRedundant climbing rather than applied. That is a healthy overlap, and restoredFromStore is what stops the next forward jump being misread as loss.

The drain

Buffering alone would stall forever. The drain is what makes out-of-order delivery invisible instead of merely survivable: the moment the missing event lands, everything queued behind it is applied in one pass, and the UI renders once.

let current = applyToThread(thread, event);
stats.applied += 1;

while (current.buffered.length > 0) {
  const nextIndex = current.buffered.findIndex((held) => held.seq === current.lastSeq + 1);
  if (nextIndex === -1) break;                   // gap still open — stop

  const held = current.buffered[nextIndex]!;
  const remaining = current.buffered.filter((_, i) => i !== nextIndex);
  current = { ...applyToThread(current, held), buffered: remaining };
  stats.applied += 1;
}

Each iteration applies one held event, which advances lastSeq, which may make the next held event eligible. It terminates for a boring but important reason: every iteration removes exactly one element from a finite array.

The claim this makes testable

Because the drain is synchronous and pure, "the network delivered these frames in this order" becomes an array literal. No browser, no timing, no flake — which is why the ordering tests can afford to be exhaustive.

Six things that read wrong at first

Each of these looks like a bug until you see why it isn't. They're the likeliest places to be caught out if someone reads the file over your shoulder.

  1. An ignored status transition still advances lastSeq. applyToThread sets lastSeq = event.seq before the switch, so a thread.status whose transition is illegal changes nothing about the status but still consumes the sequence number. That's correct — the event was delivered. If it didn't advance, every event after it would look like a gap and the thread would stall.
  2. stats.buffered is a cumulative counter, not the current depth. It counts how many times an event has ever been held. Draining doesn't decrement it. For current depth, read thread.buffered.length.
  3. thread.created bypasses the sequence gates entirely. It's handled inside gate 1's branch, so its seq is never compared to anything. In practice the server always emits it as seq 1; the reducer doesn't depend on that, it just takes whatever seq the creation event carries as the starting point.
  4. timeline is shared by reference until it changes. applyToThread starts with timeline: thread.timeline — the same array — and only replaces it with a new one when a genuinely new message or tool appears. Cheap, and still never mutated.
  5. The client ignores illegal status transitions; the server throws on them. Same table, opposite policies, on purpose. A browser has to survive a replayed or version-skewed stream. A server that sees one has a mis-classifying adapter and should fail loudly.
  6. Two threads both counting seq 1, 2, 3 is correct. lastSeq lives on the thread, not on the feed. Ordering is only ever defined within a thread — "thread A's token 3 came before thread B's token 2" isn't a fact worth having, and the connection-level offset handles resume separately.

Trace these yourself

Cover the traces above and work them out on paper. If you can do these cold, you can answer anything they ask about ordering.

  1. Thread at lastSeq 3, buffer holds [6, 5]. Event seq 4 arrives. What is lastSeq afterwards, and how many times did applied increment?
  2. Same thread, same buffer, but the arriving event is seq 7. Which gate, and what does the buffer look like after?
  3. A message.complete for a messageId the client has never seen arrives at the right sequence. Does it render? What happens to timeline?
  4. Two agents stream into one thread. Both send deltas at seq 8 and seq 9 with different messageIds. Why don't their words interleave?
  5. You reconnect and the very first frame is a tool.result for a thread you don't know. Trace it, then say what the fix would be.
Answers

1. lastSeq 6; applied increments three times — seq 4 directly, then 5 and 6 drained. 2. Gate 3; buffer becomes [6, 5, 7] in arrival order, and lastSeq stays 3. 3. Yes — message.complete creates the message if it's absent and appends it to timeline, with streaming: false. 4. messages is keyed by messageId, so each author accumulates into its own entry; a single shared accumulator is exactly the bug this design avoids. 5.
