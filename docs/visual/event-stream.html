The Log Underneath

The append-only log that the feed is built on: which parts of stream systems it actually uses, how the in-process adapter works, and what the Redis one will and will not fix.

One idea, borrowed

Under the feed is the oldest idea in streaming infrastructure: an append-only log. Records go on the end, never in the middle. Each gets a position. Nothing is ever mutated. Readers are not sent anything — they hold a position and ask for what comes after it.

Kafka is that, durably and partitioned. Redis Streams is that, in memory with optional persistence. A database's write-ahead log is that. This repo is that, in an array. The array is a bad implementation of the idea, but it is genuinely the same idea, and that is what makes the substitution possible rather than a rewrite.

The one worth saying out loud

Delivery here is at-least-once, not exactly-once, and that is a choice rather than a shortfall. SSE reconnection replays from Last-Event-ID, so overlap is normal. Exactly-once over an unreliable transport is a much larger promise than it sounds; making the consumer idempotent is the cheap, robust version, and the reducer's already-applied gate is precisely that.

Two counters on one log

The single most misunderstood part of this design, and it is a direct consequence of choosing one log per session rather than one per thread.

Stream platforms make the same split. Kafka gives you a partition offset; whatever ordering your domain needs inside that partition is yours to carry. Putting each thread on its own partition would collapse the two counters into one — and cost a connection per thread, which is the thing the multiplexed design exists to avoid.

How it is implemented today

One port, one adapter. The port is the whole surface a stream has to present for this feed to work.

interface EventStream {
  append(sessionId, event): Promise<StreamEntry>;
  open(sessionId, afterOffset, onEntry): Promise<StreamSubscription>;
  close(): Promise<void>;
}

interface StreamSubscription {
  replay: StreamEntry[];   // the backlog, for the caller to write
  oldestOffset: number;    // what overrun detection reads
  flush(): void;           // release entries held during open
  close(): Promise<void>;
}

The memory adapter

An array and a Set of listeners per session. append pushes, assigns nextOffset++, splices the array down to the retention limit, then calls every listener. oldestOffset is entries[0].offset, or the next offset when the log is empty.

It is correct for one process and cannot work across instances: another instance holds a different array, so a client that reconnects there finds nothing to replay. That is the entire reason a real adapter is worth building.

Why open and flush are one operation

A subscriber needs the backlog and everything after it, with nothing lost in between. Calling replay() and then subscribe() drops whatever is appended between the two — a race that is rare, silent, and produces exactly the kind of gap the reducer then stalls on.

The one real obstacle

Redis stream IDs are <millis>-<seq>, not integers. This port's offset is a number, and that is not cosmetic: it becomes the SSE id: field, the browser echoes it as Last-Event-ID, and the resync notice does arithmetic on it — the client resumes at from - 1.

Two ways out. Keep integers by holding a per-session INCR counter alongside the stream and storing the offset as a field on each entry — one extra round trip on append, and everything above stays untouched. Or widen offset to an opaque cursor and replace from - 1 with "the entry before this one", which Redis can answer with XREVRANGE but which spreads through the protocol, the reducer and the client.

The plan is the counter. The arithmetic on offsets is load-bearing in three places, and an opaque cursor would buy nothing except fidelity to Redis's own ID format. Kafka, incidentally, has integer offsets per partition and would need none of this.

What changes, and what does not

SessionHub does not change at all — it already cannot tell what is behind the port. Neither does the reducer, the protocol, the recovery flow, or any browser test. What changes is one adapter file and a config flag, which is the claim the port was built to make good on.

What Redis still does not fix

A shared stream makes multi-instance possible and survives a restart, and it does not give the feed a message store. The stream would still be a bounded window, so a rolled-out transcript is still unrecoverable and a thread can still come back saying its messages are gone. In production the stream is a fast tail in front of a durable store; here it would still be doing both jobs. That is a separate decision, recorded as L7.

Backpressure is untouched too: a slow subscriber is still buffered without bound (L2). Redis makes that more pressing, not less, because a stalled consumer now holds a connection to shared infrastructure.

Trace these yourself

  1. Why is ordering guaranteed within a session but undefined across sessions? What would it cost to guarantee it globally?
  2. A consumer's Last-Event-ID is below oldestOffset. What does the log owe it, and what can it not provide?
  3. Why is at-least-once delivery with an idempotent consumer a better target here than exactly-once?
  4. If each thread had its own log instead of each session, which problem goes away and which appears?
Answers

1. One log per session, and a log is only ordered within itself. Global ordering would mean a single log for every user, which serialises unrelated work and makes retention a shared resource — the classic reason to partition. 2. It owes it the truth: a resync naming the oldest offset it still holds. It cannot provide the missing prefix, because retention already discarded it. 3. Exactly-once over a transport that can drop a connection mid-frame is a very large promise; making the consumer idempotent achieves the same observable result for the cost of one comparison, which is the reducer's already-applied gate. 4. The two counters collapse into one, since offset and seq would be the same number. In exchange you need a connection or a subscription per thread, which is the browser six-connection problem the multiplexed design exists to avoid.
