The whole thing, once

Six packages. One rule about what may see what, and one line separating the logic this repo actually implements from the infrastructure it stands in for.

Rule one: the client never sees ADK

apps/web and packages/protocol contain no reference to @google/adk. The UI, the reducer and every Playwright assertion are written against FeedEvent — a plain zod union.

ADK is used across the server, the agents package and the providers package. It is the agent runtime, not a detail to be hidden. The invariant worth stating is narrower and actually true: it never reaches the client, and the translation from ADK events to wire events happens in exactly one file.

PackageImports @google/adkWhy it matters

The payoff is concrete. Because the reducer cannot see an agent framework, every ordering hazard is an array literal in a test rather than a browser and a stopwatch.

Rule two: substrate sits behind a port

Anything this app does not implement itself is reached through an interface, with an emulated adapter by default and a real one behind a flag. That turns the emulation from an assumption buried in a constructor into a named, observable choice.

Why storage and delivery are one row

They were two — eventLog and fanout — and that was wrong. Of the four combinations only two are coherent: an in-memory log with shared delivery is broken, because an instance that never held the events cannot replay them to a client that reconnects there; a shared log with in-process delivery works and buys nothing.

Every real provider serves both from one primitive — Redis Streams is XADD / XRANGE / XREAD BLOCK — so splitting them advertised a seam no implementation has. "Fan-out" was also already taken here: it means a ParallelAgent running its children concurrently. The Log Underneath covers the stream itself in depth.

A thread is a conversation, not a run

The architectural consequence of letting a thread take a second message, which turned out to be one idea rather than two features.

Terminal ends a turn, not a thread

Letting a finished thread re-open forced a distinction the code had been eliding. complete and cancelled each gained exactly one outgoing edge, back to running. error gained none: a failed run left an unknown amount of work half applied, and continuing on top of it is worse than starting again.

So isTerminal and canAcceptFollowUp now disagree, on exactly one status. That is not redundancy — it is the difference between this run is over and this conversation is over, which used to be the same sentence.

And a turn may end without the thread ending

A run gated on requireConfirmation stops without finishing. Closing it out as complete would be false, and would leave it unanswerable — so awaiting_input is the one non-terminal state a turn may settle in.

It is reachable only alongside a thread.input_required event naming what would unblock it, because a pause nobody can answer is a hang. The status says stop showing a spinner; the event says what to render instead and what to send back.

What survives a change of substrate

The useful question about any of this is: if I swapped that for the real thing, would the code around it change? Where the answer is no, the mechanism is sound and the emulation is genuinely just a stand-in.

Ours, and unaffected by any provider

The wire protocol and its two counters. The four gates and the drain. The status machine and its terminal guarantee. The per-author message map that keeps parallel agents apart. The resync recovery flow. The agent graph. The eval harness. Swap every provider below the line and none of this changes.

Emulated, with a seam

Sessions, knowledge retrieval, identity, the event log. The interface exists, the emulated adapter is the default, and the real adapter is a config flag away. Nothing calling them knows which is answering.

Bounded on both axes, in memory or not

Two ceilings that a real provider does not remove, because they are the app's job either way. EVENT_RETENTION bounds how much is kept per session. An idle sweep bounds how many sessions — it drops a hub that has no subscribers and has gone quiet, and calls drop on the log with it, because the hub is a Set and a timer handle while the events are the memory.

And one ceiling per consumer: a subscriber whose write queue passes SSE_MAX_BUFFERED_BYTES is disconnected, so a client that stops reading cannot grow the process indefinitely. Swapping the memory stream for Redis does not retire any of these; it makes the last one matter more, because the resource being protected is then shared between instances.

Not emulated — simply absent

There is no message store. The event stream is the only place agent messages exist, which is why a rolled-out transcript is unrecoverable and why a thread can come back saying its messages are gone. In production the stream would be a fast tail in front of a durable store; here it is doing both jobs. That is one architectural decision, not three loose ends.

Note what it is not: a missing adapter. Every other row above is a real capability with an emulated stand-in, and swapping it changes nothing around it. This one has no port to swap. Persisting the log does not fix it either — that makes the same wrong-shaped store durable. A log answers what happened next over a window; a transcript is state read by key, kept indefinitely. See The Log Underneath.

The argument is that each port has a real second implementation in view and a contract suite both must pass.
