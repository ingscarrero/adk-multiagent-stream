Trajectory Over Answer

Two agents can give the same answer while one looked it up and the other guessed. Only the path taken tells them apart — which is why the agent evals score trajectory strictly and wording loosely.

The question a unit test cannot ask

A unit test asks whether the code does what it says. An eval asks whether the agent still behaves — and those two can diverge without a single line changing.

Every test in this repo passes if the wiring is intact. None of them notices when a prompt edit makes the router stop calling lookupOrder and start guessing an order number that happens to look right. The answer still renders. The status machine still settles. The stream is still ordered. Nothing is broken except the part that matters.

That is the gap packages/eval exists to close, and the reason it scores two things rather than one.

Worth knowing

ADK's own evaluation tooling — AgentEvaluator, evalset files, the adk eval command — ships in adk-python only. @google/adk v2.0.0 has no equivalent. This package is a small reimplementation of the same ideas in TypeScript, using ADK's metric names so the numbers mean the same thing to anyone arriving from the Python docs.

Two axes, and the quadrant that justifies both

Hence the thresholds in support.evalset.json: toolTrajectory: 1 and responseMatch: 0.5. They are deliberately lopsided. The path must be exactly right; the wording only has to be close. Phrasing is the model's business, and a reference answer is one person's guess at how to say something. Which tools ran, in which order, with which arguments, is not a matter of taste.

Where each number comes from

One agent run produces both scores, through two different filters over the same event list. Each filter is one line, and each is wrong in a way that looks fine.

FILTER 1Framework calls are ADK's, not the agent's

transfer_to_agent, adk_request_confirmation, adk_request_credential and adk_request_input are excluded from the trajectory. They appear in the event stream as ordinary function calls, and they are not decisions the agent made about the user's problem — they are the framework's control plane.

Leaving them in would mean every evalset for the router has to open with transfer_to_agent, which couples the expectations to ADK's routing implementation. Swap LlmAgent transfer for the Workflow graph API (L15) and every case breaks without the agent's behaviour changing at all.

FILTER 2Only non-partial events carry settled text

ADK emits one partial: true event per streamed chunk, then a final non-partial event carrying the whole text. Concatenating everything counts each token roughly twice — once in its chunk, once in the final event.

The failure mode is quiet, and it is quiet in the flattering direction. A doubled answer still contains every reference word, so recall stays at 1.0 while precision halves. F1 lands near 0.67 instead of 1.0 — low enough to look like ordinary model variance, high enough to keep passing a 0.5 threshold. See A Model That Never Changes Its Mind for the streaming shape both models share.

Scoring a trajectory

Per step, over the longer of the two sequences. That denominator is the whole design.

const length = Math.max(expected.length, actual.length);
if (length === 0) return 1;              // no tools expected, none called: correct

let matched = 0;
for (let i = 0; i < length; i += 1) {
  const want = expected[i];
  const got = actual[i];
  if (!want || !got) continue;           // past the end of one side: unmatched
  if (want.name === got.name && argsMatch(want.args, got.args)) matched += 1;
}
return matched / length;

Arguments compare as a subset

An actual call matches if it contains at least the expected keys with the expected values. Extra keys are allowed.

expected: { orderId: 'A-1001' }
actual:   { orderId: 'A-1001', includeHistory: false }   → matches

Strict equality would make every case brittle against a tool gaining an optional parameter — which is a change in the tool, not a regression in the agent. The evalset should fail when the agent's behaviour changes, and stay quiet when the surrounding code grows.

Scoring a response

ROUGE-1 F1 over unigrams. Not exact match, not a judge, and both of those are decisions.

precision = overlap / actual.length      // how much of the answer was in the reference
recall    = overlap / expected.length    // how much of the reference the answer covered
F1        = 2PR / (P + R)

Why F1 and not recall. Recall alone is trivially gamed: an answer that pastes the reference in among four paragraphs of filler scores 1.0. Precision punishes the padding. A correct answer phrased differently still scores well; a confidently wrong one does not.

Bag semantics, not set. The overlap counter decrements a Map of remaining reference tokens, so a word appearing twice in the reference can be matched twice and no more. A set would let one repeated word in the answer cover every occurrence.

The honest limit

ROUGE-1 is word overlap. It cannot tell "delivery is 2 September" from "delivery is not 2 September" — one token differs and F1 barely moves. That is exactly what mustContain is for: a cheap, unambiguous grounding assertion ("A-1001", "30 days") checked as a case-insensitive substring alongside the fuzzy score. Fuzzy metric for phrasing, hard assertion for facts.

Why not an LLM judge

A judge model would be more expressive and would also make the suite non-reproducible — which defeats the purpose of using it as a regression gate. The same evalset runs inside pnpm test, in CI, with no API key; a judge would mean network, cost, and a score that moves on its own between runs.

The place for a judge is a separate, opt-in run against the real model, where non-determinism is already the point.

The dual run matters more than it sounds. An evalset that only runs on demand is documentation; one that runs in CI is a contract. Putting it inside pnpm test means the 6 cases are as load-bearing as the 217 unit tests around them.

Against the runner, not the server

runEvalCase drives InMemoryRunner directly rather than going through HTTP. Evals grade the agent; routing them through the transport means a failing case could be the agent, the adapter, the hub, or the buffer. chunkDelayMs: 0 for the same reason — streaming timing is the browser suite's problem, not this one.

Trace these yourself

  1. Change lookupOrder to take { id } instead of { orderId }, leaving everything else alone. Which score moves, and which stays at 1.00?
  2. Delete the .filter((event) => !event.partial) in runner.ts and run pnpm eval. Predict the direction the response scores move before you look — then check whether any case actually fails.
  3. no-tools-needed expects an empty trajectory and scores 1.00. What would the score be if toolTrajectoryScore returned 0 for the empty case instead, and which of the six cases would still pass?
  4. Add transfer_to_agent back into the expected trajectory of warranty-policy. It genuinely happens at runtime — so why does the case now fail?
